01 · WHAT

Pi：一个可以做成你自己的 Agent Harness

官方定位是 minimal、extensible：默认够用，但刻意不把一切都内置。

强默认

开箱即用的 coding agent CLI，内置 read、bash、edit、write 等基础工具。

刻意留白

不内置 sub-agents、plan mode，也不内置权限系统。需要时用扩展或 package 补上。

按工作流定制

extensions、skills、prompt templates、themes 可打包成 Pi packages，经 npm 或 git 分发。

代价同样明确：灵活性交给使用者，边界与治理也交给使用者。

来源：earendil-works/pi README；docs/packages.md

01 · WHAT

同一个内核，四种用法

interactive

交互式 TUI

日常使用。1.0.0 起默认全屏，可改回常规滚动模式。

print / JSON

脚本与自动化

非交互运行，输出可被脚本和流水线消费。

RPC

被外部进程控制

宿主程序通过 RPC 驱动 Pi，适合嵌进自己的界面。

SDK

TypeScript SDK

把 agent 当库来用，自己做应用。官方举的真实集成例子是 OpenClaw。

四种用法共用同一个 agent loop：loop 只产出事件，界面和传输方式都在它之外。

来源：earendil-works/pi README

01 · WHAT

分层架构：按真实依赖画

pi-coding-agent

CLI、TUI、RPC、SDK；会话、内置工具、skills、扩展

pi-agent-core · pi-tui · pi-mcp · pi-codemode

coding-agent 的直接依赖：agent loop、终端 UI、MCP 客户端、沙箱脚本

pi-ai

统一的多 provider LLM API，依赖 pi-telemetry

coding-agent 直接依赖以上全部；中间一层只有 agent-core 依赖 pi-ai，tui、mcp、codemode 不依赖其他内部包

pi-durable（实验性）

与 agent-core 平行的另一套 harness：先提交再展示，崩溃后从 checkpoint 继续。

依赖 pi-ai、pi-codemode、chord；不在 coding-agent 的依赖链上。

chord

可热更新插件、复制状态、JSON 链路 RPC。1.2.0 起 coding-agent 不再依赖它。

来源：main 分支（v1.2.0）各包 package.json 的 dependencies；README「Packages」

03 · LOOP

loop 上的四个可控点

transformContext → convertToLlm

每次调用前先裁剪、注入上下文，再过滤掉 UI 专用消息，把自定义消息转成 LLM 能懂的三种角色。

toolExecution: parallel

默认并发执行工具，结束事件按完成顺序发，toolResult 消息仍按助手原顺序落盘。

beforeToolCall / afterToolCall

前者可拦截执行，后者可改写结果；整批都返回 terminate: true 时，跳过后续 LLM 调用。

steer() / followUp()

steer 等本批工具执行完才注入，下个 turn 生效；followUp 只在 agent 本要停下时才检查。

来源：packages/agent/README.md；src/agent-loop.ts（agentLoop）、src/agent.ts（Agent 类）

03 · EXTENSIONS

最小的扩展：导出一个工厂函数

import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {

pi.registerCommand("hello", {

description: "Show a greeting",

handler: async (name, ctx) => {

ctx.ui.notify(`Hello, ${name || "world"}!`, "info");

},

});

}

放进 ~/.pi/agent/extensions/，或用 pi --extension ./hello.ts 直接加载。

用 jiti 加载，本地 TypeScript 不需要单独编译。

工厂里不要起进程、定时器，放到 session_start 里。

03 · EXTENSIONS

边界：Pi 不替你画，要自己画

Pi 不内置权限系统，以启动它的用户权限运行；文件、进程、网络、凭据都不设限。

扩展在 Pi 进程里运行，能读到提示词、工具调用、文件、凭据和会话历史。

tool_call 钩子能做确认和拦截，但它是进程内的约束；要隔离，靠容器或沙箱。

Gondolin 扩展

Pi 与凭据留在宿主，内置工具和 ! 命令走本地 Linux micro-VM

Plain Docker

整个 Pi 进程放进本地容器，最简单

Docker Sandboxes

托管沙箱，provider 凭据留在宿主、由代理替换

OpenShell

整个 Pi 进程放进带策略的沙箱，本地或远程

来源：README「Permissions & Containerization」；docs/extensions.md；docs/containerization.md

会话是一棵树，模型只看当前分支

存储方式

条目按树存储，回到早先节点不会删掉离开的分支。

03 · SESSIONS

进程挂了能接上吗？三种做法

内置：会话级恢复

会话自动落盘为 JSONL，pi --continue 接上对话。

中断的工具调用不会续跑；发给模型前，pi-ai 为它补一条 “No result provided” 错误结果。

扩展：事后补救

demo 里的 resume 扩展：checkpoint 写进 JSONL，重启时找出悬空的调用。

用 context 钩子补一条“已中断”结果，不改 Pi 源码。

Pi Durable：存储层

输出、工具调用、队列先提交到存储，再展示；崩溃后从最后一个 checkpoint 继续。

只有声明 replay: "safe" 的工具会重跑，其余拿到 interrupted 结果。

现状：Pi Durable 随 1.0 发布，官方标注实验性，API 会变。存储支持 Memory、SQLite、JSONL、Cloudflare Durable Object。会重跑的工具若有副作用，要自己保证幂等。

来源：earendil.com/posts/pi-durable；packages/durable/README.md；pi-ai src/api/transform-messages.ts

05 · NEXT

我们可以从哪里开始探索

方向 A

嵌进研发流程

print / JSON 与 RPC 模式让 Pi 可被脚本、CI 和其他程序驱动；官方另有 pi-chat 仓库做聊天自动化。

方向 B

接入内部工具与数据

用自定义 tool 或 MCP server 把内部系统交给 agent，入口是 registerTool 与 registerMcpServer。

方向 C

长期运行的助手

任务可中断、可恢复。Pi Durable 已有实验性实现，适合跟踪和小范围试验。

采用前提：生态活跃，仓库约 11.5 万 star；迭代也很快，9 月 29 日到 10 月 12 日发了 10 个版本（0.99.0 → 1.2.0），破坏性变更不少，升级前先读 changelog。

来源：earendil-works/pi README 与 Releases；docs/extensions.md；packages/durable/README.md
